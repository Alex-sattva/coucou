Intent router — Claude now, Jev later

One decision step replaces the hand-written phrase rules. The brain is swappable: Rules (offline), Claude, and later Jev.

Goal

Today Mochi decides what to do with what you say through a growing pile of phrase rules. A router replaces them. It receives what you said plus the current state, and returns one action from a fixed list. Coucou's own code carries that action out. Jev slots in later as a third backend, touching nothing outside its own file.

Architecture

bar Enter / voice end
   └─ AssistantModel.submitTask(text)
        └─ RouterInput (utterance + sessions + projects + mainId)        [pure]
             └─ IntentRouter backend (Settings: Rules | Claude)
                  ├─ ClaudeRouter — HTTP, 4 s timeout, any failure → RuleRouter
                  └─ RuleRouter   — today's rules
             └─ RouterDecision.validated(against: input)                 [pure]
        └─ AssistantModel.execute(decision)
             reply   → send to the session (unchanged path)
             start   → existing confirm card (click required)
             open    → open the session in the terminal
             clarify → new clarify card, each choice = a concrete action
             none    → "I'm not sure what to do with that"

Types (pure, in AssistantLogic.swift)

struct RouterInput { utterance, sessions: [RouterSession], projects: [RouterProject], mainSessionId }
enum RouterAction {
    case reply(sessionId, text)
    case start(projectPath, cli?, prompt?)
    case open(sessionId)
    case clarify(question, choices: [RouterChoice])   // 2–4, never nested
    case none
}
struct RouterDecision { action, source }   // "rules" | "claude"
RouterDecision.validated(against:)         // unknown ids never reach execution

Claude backend

  • Plain HTTP to the Messages API with the Anthropic key ClaudeService already stores in the Keychain.
  • Model claude-opus-5-5, effort low, structured JSON output. No thinking field and no forced tool_choice (both rejected on this model). The model id is one constant.
  • The schema is fixed. Session ids and project paths are plain strings, checked against the real lists afterwards. Putting them in the schema would recompile it on every change.
  • The prompt says to copy ids exactly, never to rewrite your words, and to prefer asking over guessing.
  • Any failure (no key, 4 s timeout, network, refusal, bad JSON) falls back to Rules and logs one line. Your words are never logged.

What leaves the Mac

Only what you said; for each running session its id, agent, workspace, folder, phase, title and last prompt (up to 200 characters); up to 40 projects (name, path, last CLI); the main session id. No transcripts, replies or file contents.

Steps

1 · Pure types, RuleRouter, validation

Add the types, RuleRouter.decide (today's behaviour, exactly) and validated.

Account for: filler-only text; a project named while a session runs (reply unless the text starts with a trigger); unknown ids in clarify choices; nested clarify; empty choices.

Test script prints All tests passed., with every action and every validation rule covered.

2 · Claude response parsing (pure)

ClaudeRouterParsing.decision(fromJSON:) and requestBody(input:), both testable without the network.

Account for: nulls where an action needs a field; an unknown CLI string; clarify inside choices; non-ASCII text; escaped slashes.

Tests pass: one fixture per action, plus three malformed ones that throw.

3 · Backends + model wiring

IntentRouter.swift holds the protocol, ClaudeRouter and RuleRouter. submitTask becomes build input → route (with fallback) → validate → execute.

Gotchas: the model runs on the main actor, so the HTTP call runs in a Task. The router never approves permissions or answers question cards.

Builds. With Settings = Rules, nothing behaves differently from before.

4 · Clarify card

The question (wraps, never cut off) and 2–4 choice rows styled like the question card. Keys 1–4 pick, Esc closes. A "start" choice still goes through the confirm card. No footer.

Tests pass, including a height test. Manual check 3.

5 · Settings + privacy

General → "Understanding": a Rules / Claude picker. Claude is disabled without a key. Default is Rules. Add a paragraph to docs/privacy.html saying what is sent.

Builds; the picker shows; the privacy paragraph renders.

Manual verification

  1. Nothing running: "In Bapoojee where is the document to send to the CEO" → confirm card with the sentence as first message.
  2. A coucou session running: "start the tests" → sent to that session, not a launch.
  3. "Work on the dashboard" with two matching projects → clarify card → pick one → confirm card.
  4. Wi-Fi off → behaves like Rules, with one fallback line in the log.
  5. Settings = Rules → identical to today.

Out of scope / Do NOT

  • No overseer behaviour. The router only acts on something you said.
  • Never approve a permission, answer a question card or send an email from a router decision.
  • No Jev code yet. Just keep the protocol free of Claude-specific types.
  • No per-request schema enums, no streaming, no memory between utterances.
  • Don't restyle existing cards. Don't touch the wake-word or ⌥ code.
  • No telemetry. Never log what the user said.
